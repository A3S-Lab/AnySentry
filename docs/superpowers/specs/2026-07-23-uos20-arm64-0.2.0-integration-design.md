# AnySentry UOS 20 ARM64 0.2.0 集成与离线部署设计

## 1. 目标

在不修改 AnySentry、Observer、Sentry 上游开发分支的前提下，将下列能力集成为可离线安装和升级的 UOS 20 ARM64 发布包：

- AnySentry `origin/main` 最新正式能力；
- `@a3s-lab/sentry` TypeScript SDK 0.2.0 与 Rust crate 0.7.0；
- Observer `origin/main` 最新 exec argv、workload observation 和进程归因能力；
- UOS Linux 4.19 legacy eBPF 采集后端；
- 内置 ClickHouse、Redis、Node.js、Sentry ARM64 N-API、L3 ARM64 模块；
- AnySentry API、fast-judge worker、l3-worker、Observer 的 systemd 服务；
- 首次安装、原地升级、失败回滚、主机诊断和验收。

本发布不包含 `release/internOS-v0.1.0` 的 Open Platform 专用能力。

## 2. 已确认上游基线

设计确认时的远程提交如下：

```text
AnySentry origin/main:
f8fcfc84733f193a06ba3e81dc6938fc2ace0c1a

AnySentry async judgment merge source:
44515448d85e741c2b4ae4f9dffb1a85e8fed714

Observer origin/main:
6a6ef5eeee4f7c6ede0f9e2216adbc94c9e8db9e

Sentry origin/main:
c1b45120662224fe1f3065d6888da0d291b4ff07
```

AnySentry `origin/main` 的 `f8fcfc8` 是异步判定 PR #3 的 merge commit。`4451544` 已是 `origin/main` 的祖先，且 AnySentry 已依赖 `@a3s-lab/sentry` 0.2.0。因此集成时只合并 `origin/main`，不得重复合并 async feature branch。

正式构建不得依赖可移动分支名称。开始实现后，应将审核通过的精确提交写入版本锁定文件和 `PROVENANCE`。

## 3. 分支和 worktree 模型

### 3.1 AnySentry

稳定部署分支：

```text
build/uos20-arm64-package
```

本轮临时集成分支：

```text
integration/uos20-arm64-0.2.0
```

对应 worktree：

```text
/home/chensicheng/.config/superpowers/worktrees/AnySentry/uos20-arm64-package
/home/chensicheng/.config/superpowers/worktrees/AnySentry/uos20-arm64-0.2.0
```

稳定 worktree 保持上一发布状态。所有 merge、冲突处理和新部署组件先在 integration worktree 完成。只有在构建验证和目标环境验证全部通过后，才将 integration 分支合回稳定 build 分支并创建发布 tag。

### 3.2 Observer

稳定 UOS legacy 分支：

```text
build/uos20-arm64-legacy
```

本轮临时集成分支：

```text
integration/uos20-arm64-0.2.0
```

对应 worktree：

```text
/home/chensicheng/.config/superpowers/worktrees/Observer/uos20-arm64-legacy
/home/chensicheng/.config/superpowers/worktrees/Observer/uos20-arm64-0.2.0
```

Observer `origin/main` 只合并到 integration 分支。legacy backend 适配并完成目标内核验证后，再合回稳定 UOS legacy 分支。

### 3.3 Sentry

Sentry 不建立长期 UOS 功能分支。构建程序从锁定的 `origin/main` 提交导出源码，交叉编译 Linux ARM64 N-API 模块。

## 4. 集成策略

### 4.1 基线固化

最后交付的 compat2 构建层位于 `security/uos20-arm64/`，该目录不属于 AnySentry Git 仓库。开始 merge 前，必须先将其中已经验证的构建、安装、诊断和回滚能力迁入 AnySentry integration 分支并提交。

基线固化内容至少包括：

- current-HEAD/固定提交源码导出；
- ARM64 Sentry 构建；
- ClickHouse `armv8.0-compat` 构建；
- Observer hotfix3 和 `0x0004135a`；
- raw BPF syscall probe；
- glibc 2.28 和 64 KiB ELF 检查；
- 事务化 installer；
- 配置增量合并；
- 自动 rollback；
- Observer Source HTTP 201/响应信封兼容；
- manifest、VERSION 和 PROVENANCE；
- Source/collector 运行验证；
- ClickHouse 自观测噪声过滤；
- 主机检查和部署文档。

### 4.2 AnySentry merge

在 AnySentry integration 分支执行一次显式 merge：

```text
build/uos20-arm64-package
        +
origin/main @ f8fcfc8
```

不得再次合并 `origin/fix/anysentry-async-judgment`。

冲突解决必须保留两类语义：

1. 上游异步判定语义：
   - Redis/BullMQ 队列；
   - fast/L3/result queue；
   - decision lifecycle；
   - Sentry 0.2.0；
   - L3 Agent Pool；
   - worker-main；
   - Observer 归因和去重。
2. UOS 部署语义：
   - 受保护环境文件；
   - LLM 密钥不持久化；
   - `/opt/anysentry`、`/var/lib/anysentry` 固定路径；
   - ARM64 L3 原生模块；
   - 内网和离线运行；
   - L2/L3 超时；
   - 初始 L1-only 安全模式。

不允许对冲突文件整体选择 `ours` 或 `theirs`。

### 4.3 Observer merge

在 Observer integration 分支合并 `origin/main @ 6a6ef5e`，保留：

- 最新公共事件模型；
- exec argv 捕获；
- workload observation；
- process/workload attribution；
- 最新 collector 健康模型；
- `legacy-kernel-4-19` feature；
- perf-kprobe legacy runtime；
- 外部、已验证的 `probes-legacy.o`；
- UOS BPF version code `0x0004135a`。

最新 userspace collector 与 legacy BPF 对象之间的事件结构必须逐字段一致。若某项最新 Observer 能力不能由 Linux 4.19 legacy probe 提供，发布文档和健康接口必须明确标记为降级或不可用，不能报告虚假健康。

### 4.4 Sentry 0.2.0

从锁定的 Sentry 提交构建：

```text
a3s-sentry.linux-arm64-gnu.node
```

构建输出必须：

- ELF Machine 为 AArch64；
- 最高 GLIBC 版本不超过 2.28；
- LOAD 对齐支持 65536 页；
- 不包含 x86_64 native 模块；
- 能被随包 Node.js 实际加载；
- 通过 Sentry 0.2.0 API、异步判定和 policy envelope 契约测试。

## 5. UOS 目标环境

目标机器基线：

```text
OS: UnionTech OS Server 20 Enterprise
CPU: Kunpeng 920, aarch64, ARMv8.0 baseline
CPU cores: 16
Memory: approximately 64 GiB
glibc: 2.28
page size: 65536
uname kernel: 4.19.0-arm64-server
BPF accepted kernel version: 4.19.90
BPF kern_version code: 0x0004135a
BTF: unavailable
network: offline/internal network
```

目标环境为空白机器，发布包不得依赖 apt、yum、npm、pnpm、cargo、Docker 或公网下载。

## 6. UOS 兼容性要求

### 6.1 CPU 和 ELF

所有目标机原生程序采用 ARMv8.0 基线，不得使用 `-mcpu=native`。对每个 ELF 验证：

- AArch64；
- GLIBC 不高于 2.28；
- 64 KiB page alignment；
- 动态解释器存在；
- 无外来 x86_64 ELF；
- 无悬空符号链接。

### 6.2 ClickHouse

保留 ClickHouse 24.8 `armv8.0-compat` 构建。安装前实际执行 `clickhouse --version`，将 SIGILL 阻断在停服之前。

### 6.3 Redis

发布包内置 ARM64 Redis server 和 CLI，使用 ARMv8.0、glibc 2.28、64 KiB 对齐构建。Redis 数据目录为：

```text
/var/lib/anysentry/redis
```

日志目录为：

```text
/var/log/anysentry/redis
```

启用 AOF 持久化。Redis 只监听 loopback，不对外开放 6379。Redis 源码版本、源码校验和、编译器和构建参数写入 `PROVENANCE`。

### 6.4 Observer Linux 4.19

保留：

- BPF ISA v1；
- `-target bpfel -mcpu=v1`；
- 无 `.BTF`、`.BTF.ext`；
- ARM64 `pt_regs` syscall 参数读取；
- `__arm64_sys_*` 和 `do_exit` 符号；
- per-CPU scratch maps；
- perf event array；
- raw BPF syscall preflight；
- 8 个 legacy probe 附加验证；
- 无有效 probe 时拒绝健康。

### 6.5 自观测噪声

默认过滤：

```text
/sys/
/proc/
/run/
/dev/
/var/lib/anysentry/clickhouse/
/var/log/anysentry/
/var/lib/anysentry/redis/
```

Redis AOF/RDB 和 ClickHouse 数据文件不得进入安全事件流。

## 7. 服务拓扑

目标 systemd 服务：

```text
anysentry-clickhouse.service
anysentry-redis.service
anysentry.service
anysentry-fast-judge.service
anysentry-l3-worker.service
anysentry-observer.service
```

依赖关系：

```text
ClickHouse ───────┐
                  ├── AnySentry API ─── Observer
Redis ────────────┤
                  ├── fast-judge
                  └── l3-worker
```

初次升级默认：

```ini
ANYSENTRY_ASYNC_JUDGE=off
```

Redis 和 worker 随包安装。worker 可连接 Redis 并保持空闲，但 API 在 L2/L3 未配置时不投递异步作业。配置内网 LLM 并验证连接后，再开启异步判定。

## 8. 安装、升级和回滚

安装程序同时支持首次安装和从 compat2 升级：

1. 校验 tar SHA-256 和内部 manifest；
2. 检查主机 ABI、CPU、glibc、页大小和磁盘；
3. 执行 Node、ClickHouse、Redis、Observer 版本命令；
4. 执行 raw BPF syscall probe；
5. 验证 BPF `4.19.90 / 0x0004135a`；
6. 合并新增环境变量，不覆盖原密码、Source token 和 LLM 密钥；
7. 备份旧程序、旧 systemd 单元和配置；
8. 停止 Observer、worker、API、Redis、ClickHouse；
9. 原子切换程序；
10. 按 ClickHouse、Redis、API、worker、Observer 顺序启动；
11. 执行完整 verify；
12. 任一步失败时恢复旧程序和旧 systemd 单元。

ClickHouse 变更限于 `ADD COLUMN IF NOT EXISTS` 等向后兼容迁移。Redis 新数据目录在 rollback 时保留，但旧 compat2 服务不启动 Redis。

### 9.1 构建验证

- 三个上游输入 commit 精确锁定；
- merge 冲突全部有语义测试；
- AnySentry build 和既有 contract tests；
- Observer main tests 和 legacy tests；
- Sentry 0.2.0 tests；
- Redis build/smoke；
- 所有 ELF ABI；
- BPF 对象结构和 version；
- 包内无开发依赖、绝对构建路径和秘密；
- manifest 和 PROVENANCE。

### 9.2 UOS 目标机预检

- architecture、glibc、page size；
- CPU 指令执行；
- ClickHouse、Redis、Node、Observer version；
- BPF maps、socket filter 和 kprobe；
- tracefs/debugfs、kprobe symbols；
- capability、seccomp、LSM；
- 端口和数据目录。

### 9.3 运行验证

- ClickHouse ping；
- Redis PING、AOF 写入和重启恢复；
- API health；
- Sentry 0.2.0 L1 decision；
- Source active、acceptedEvents 增长、rejectedEvents 不增长；
- 8 个 legacy probes；
- Observer 最新 exec argv；
- workload identity 能力矩阵；
- fast worker queue；
- L3 worker queue；
- result lifecycle 回写 ClickHouse；
- outputDropped、errorCount、queueDepth；
- LLM 未配置时 L1-only；
- LLM 配置后 async L2/L3；
- 安装失败自动 rollback；
- 新版本启动失败自动 rollback；
- 旧 compat2 在回滚后仍可读取 ClickHouse。

## 10. 发布和分支晋级

集成验证完成后：

1. AnySentry integration 分支合回 `build/uos20-arm64-package`；
2. Observer integration 分支合回 `build/uos20-arm64-legacy`；
3. 分别创建不可移动的 UOS 发布 tag；
4. 完整构建正式 tar 包；
5. 在 `PROVENANCE` 记录所有仓库提交和依赖；
6. 上传服务器并执行 `install.sh --check`；
7. 通过后执行 `install.sh`；
8. 保存目标机验收报告。

稳定 build branch 仅接受通过构建验证和目标机验证的 integration merge。

## 11. 非目标

- 不将 UOS 专用代码合入 AnySentry、Observer、Sentry 的通用 main；
- 不包含 `release/internOS-v0.1.0` Open Platform 能力；
- 不依赖目标机 Docker；
- 不依赖目标机包管理器或公网；
- 不在 LLM 未配置时默认打开异步作业投递；
- 不通过跳过 ABI/BPF 检查强制安装。
